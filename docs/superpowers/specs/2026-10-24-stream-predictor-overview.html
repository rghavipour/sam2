SAM2 Stream Predictor

یک predictor جدید برای ردیابی زنده روی SAM 2 اصلی. هدفش حل دو محدودیت dahi-live-ai است: فقط یک object در هر سشن، و افت FPS با زیاد شدن سشن‌ها.

خلاصه

سرویس الان روی SAM2CameraPredictor از fork Gy920/segment-anything-2-real-time کار می‌کند. این fork منطق قدیمی SAM 2 (قبل از 12/2024) را دارد. objectها فقط قبل از اولین track() اضافه می‌شوند، و state هر سشن روی خود شیء predictor نگه داشته می‌شود.

این branch یک SAM2StreamPredictor تازه روی upstream (facebookresearch/sam2) می‌سازد:

  • هر object مستقل است و در هر frame اضافه، اصلاح یا حذف می‌شود.
  • state سشن بیرون از مدل است، پس یک نسخه از وزن‌ها برای همهٔ سشن‌ها کافی است.
  • حافظه سقف ثابت دارد و هیچ تصویری نگه داشته نمی‌شود.
  • objectهای یک سشن با هم batch می‌شوند و image encoder فقط یک بار برای هر frame اجرا می‌شود.

خود مدل و وزن‌ها دست نمی‌خورند و خروجی باید با SAM2VideoPredictor upstream یکی باشد. تست parity همین را ثابت می‌کند.

دو محدودیت فعلی و شواهدشان

۱. با سشن بیشتر FPS می‌افتد و GPU قوی‌تر کمکی نمی‌کند

اعداد این بخش از SLA report تاریخ 2026-09-24 خود dahi-live-ai است: RTX 3080 Ti، SAM 2.1 small، ورودی 512، stream با 640x480 در 15 FPS.

  • SAM 2.1 small در 512 روی این کارت باید حدود ۱۰ تا ۲۰ میلی‌ثانیه کار GPU داشته باشد. ولی یک frame با یک room حدود 106ms طول می‌کشد.
  • همهٔ roomها در یک process پایتون و یک GIL اجرا می‌شوند. PyTorch در حالت eager صدها kernel کوچک launch می‌کند و هزینهٔ launch روی CPU است.
  • ستون «on device» در report با wall time برابر است (106.1 در برابر 106.2). CUDA event دور کل track() گذاشته شده و زمان‌هایی را هم می‌شمارد که GPU منتظر CPU است. پس نتیجه‌گیری «سقف compute-bound سخت‌افزار» در لاگ refactor از همین خوانش غلط آمده.
  • vos_optimized در fork هیچ ماژولی را compile نمی‌کند. پس در عمل نه compile داریم، نه CUDA graph.

این تحلیل از اعداد خود report استنتاج شده و هنوز با torch.profiler روی GPU تأیید نشده. اولین کار روی سرور همین اندازه‌گیری است.

۲. فقط یک object در هر سشن

  • لایهٔ app: GPUTracker و SimpleTracker فقط یک active_state دارند. batch_add_objects فقط آخرین object را نگه می‌دارد و datachannel_handler هر add_object جدید را جایگزین قبلی می‌کند.
  • لایهٔ fork (علت اصلی): بعد از اولین track()، فلگ tracking_has_started=True می‌شود و object جدید خطا می‌دهد. تنها راه reset و load_first_frame است که memory همهٔ objectها را پاک می‌کند. re-anchor با ReID هم همین مسیر را می‌رود.
  • باگ‌های fork: add_all_frames_to_correct_as_cond تعریف نشده، bbox از نوع tensor بی‌صدا نادیده گرفته می‌شود، و add_new_prompt_during_track در هر سه مسیرش خطا می‌دهد.

معماری: قبل و بعد

API و چرخهٔ هر frame

predictor = build_sam2_stream_predictor(config, ckpt, device="cuda")
session = predictor.create_session(max_objects=3)

predictor.set_frame(session, frame)          # uint8 RGB, HxWx3
predictor.add_prompt(session, obj_id=1, box=[x1, y1, x2, y2])
out = predictor.track(session)               # StreamOutput
# out.obj_ids, out.mask_logits [N,1,H,W], out.object_score_logits [N,1]

out = predictor.step(session, next_frame)    # set_frame + track
predictor.reset_object(session, 1)           # re-anchor: memory cleared, id kept
predictor.remove_object(session, 2)
  1. set_frame frame قبلی را نهایی می‌کند: promptهای در انتظار encode می‌شوند و در memory ثبت می‌شوند. بعد memory قدیمی‌تر از پنجره حذف می‌شود، frame جدید روی GPU resize و normalize می‌شود و فیچر backbone یک بار حساب می‌شود.
  2. add_prompt روی frame فعلی کار می‌کند. id جدید یعنی object جدید و این frame cond frame آن می‌شود. اگر object روی همین frame قبلاً track شده باشد، prompt یک اصلاح (correction) حساب می‌شود. نتیجه موقتاً نگه داشته می‌شود تا کلیک‌های بعدی هم ممکن باشد.
  3. track برای همهٔ objectها mask برمی‌گرداند. objectهایی که prompt دارند همان خروجی را می‌گیرند. بقیه بر اساس شکل memory گروه‌بندی می‌شوند و هر گروه یک بار از memory attention، SAM heads و memory encoder رد می‌شود.

تست و معیار درستی

  • روی CPU همین ماشین: مدل tiny با وزن تصادفی در 256 پیکسل، با پیکربندی‌های موجود و hydra override. وزن‌ها با load_state_dict بین predictor جدید و SAM2VideoPredictor upstream یکی می‌شوند، پس مقایسه دقیق است.
  • parity یک object: logits در fp32 با atol=1e-4 برابر upstream.
  • parity سه object batch‌شده: IoU ≥ 0.99 برای هر object در هر frame. objectی که وسط stream اضافه می‌شود با یک سشن upstream مقایسه می‌شود که فقط همان object را دارد و از همان frame شروع می‌کند.
  • رفتار: حذف و اضافهٔ دوباره، re-anchor، کلیک اصلاحی، تغییر اندازهٔ frame، track بدون object، دو بار track روی یک frame، و stream دویست‌فریمی که حافظه‌اش نباید رشد کند.
  • روی سرور GPU: checkpoint واقعی SAM 2.1 روی ویدیوی bedroom، parity در bf16 با IoU ≥ 0.98، و benchmark یک و سه object در 512 و 1024، با زمان‌گیری sync‌شده و جدول torch.profiler.

Best practice

مدل و سشن

  • یک مدل برای هر process، یک StreamSession برای هر room. مدل را هیچ‌وقت copy نکنید.
  • هر session در هر لحظه فقط از یک thread استفاده شود. مدل مشترک و فقط‌خواندنی است.
  • همهٔ سشن‌های یک process یک اندازهٔ ورودی (مثلاً 512) داشته باشند. RoPE با تغییر اندازه جدول خودش را دوباره می‌سازد.
  • max_objects را صریح تنظیم کنید. فعلاً ۳.
  • با پایان room، session را رها کنید و هیچ tensorی از آن را در state برنامه نگه ندارید.

ورودی و خروجی

  • frame باید uint8 با ترتیب RGB باشد. frame خروجی OpenCV را قبلش از BGR به RGB تبدیل کنید.
  • روی CUDA از torch.autocast(dtype=torch.bfloat16) و torch.inference_mode() استفاده کنید.
  • logits را روی GPU با آستانهٔ 0 باینری کنید و فقط یک بار داده را به CPU منتقل کنید. اگر کافی است، از ماسک low-res استفاده کنید.
  • برای re-anchor از reset_object و بعد add_prompt استفاده کنید، نه load_first_frame.

اندازه‌گیری

  • زمان را با torch.cuda.synchronize() یا torch.profiler بگیرید. CUDA event دور یک call پایتون، زمان CPU را هم می‌شمارد.
  • عدد SM در nvidia-smi فقط می‌گوید آیا kernelی در حال اجرا بوده یا نه. معیار ظرفیت نیست.
  • هیچ ادعای FPS بدون benchmark روی سخت‌افزار واقعی ثبت نشود.
  • parity را بعد از هر تغییر در مسیر inference دوباره اجرا کنید.

استقرار

  • fork را در Dockerfile با commit SHA pin کنید، نه با main.
  • تا آماده شدن engine مشترک، roomها را بین چند process پخش کنید و NVIDIA MPS را روشن کنید.
  • روی stream خیلی طولانی، فاصلهٔ زمانی تا cond frame بی‌سقف بزرگ می‌شود (مثل upstream). یک سیاست re-anchor دوره‌ای در app بگذارید.
  • VRAM را بعد از teardown با torch.cuda.memory_allocated() چک کنید، نه فقط با nvidia-smi.

ریسک‌ها و موارد باز

سرور GPU: host key سرور 94.184.177.89 عوض شده است. تا وقتی کلید جدید تأیید نشود، هیچ تستی روی GPU اجرا نمی‌شود.

  • resize روی GPU با bilinear antialias انجام می‌شود ولی loader upstream از PIL استفاده می‌کند. تفاوت کمی در پیکسل‌ها می‌دهد. تست parity این مرحله را دور می‌زند و تست جدایی فاصلهٔ آن را محدود می‌کند.
  • batch در bf16 روی GPU می‌تواند اختلاف عددی کوچکی بدهد. معیار IoU ≥ 0.98 برای همین است.
  • سقف ۴ cond frame برای هر object انتخاب خودمان است. upstream سقفی ندارد.
  • کلیک روی frameی که هنوز track نشده یک cond frame جدید می‌سازد (قانون upstream). این رفتار را در app مستند کنید.
